# 独立修改与并行反馈

## 示例

本例为虚构任务列表应用，代码/命令是教学输入，不是本项目执行证据。用户请求：只移除导入文本首字符 BOM；空列表显示“还没有任务”并说明已有导入按钮；保留未提交修改。若用户只要计划，先停在计划。

Lead 最小读取 AGENTS、parser、空态和现有测试。parser 归 A，空态归 B，文件/业务状态独立，有并行收益；若已有项目角色授权就沿用，否则明确 Worker 和 Reviewer。不是所有任务都要两个 Worker。交接包含真实绝对工作区、分支/基准、用户改动、唯一所有权、验收和指定验证，Codeg 不自动提供 worktree。

```ts
const normalized = text.startsWith('\uFEFF') ? text.slice(1) : text;
return normalized.split(/\r?\n/);
```

只去掉首字符，保留中间 BOM、其他文字和顺序。A 集中修改解析及必要既有断言，按指定 parser 测试自测；B 沿用真实导入动作，构建并给用户查看文案/位置/点击步骤，不创建截图矩阵。不得把这段片段当成已有生产接口或宣称本仓库执行过应用测试。

A 先完成即报行为、版本、命令真实结果、候选和未完成，继续跟进 B。用户补充“空态保留现有字体”，Lead 把原话与范围传 B，确认收到；A 的有效结论保留。已安排 Reviewer 可接续审 A；未明确时只暂停 A 相关决定，B 独立继续。有任务运行时 Lead 不提前结束协调。

Reviewer 对照真实 diff/正确基线，检查 A 的首字符边界、B 的现有真实按钮入口，复用有效自测。必要审查 PASS 后 Lead 按依赖集成，做一次组合相关检查。只有测试进入了目标路径才记录通过；最终版本必须对应审查对象。

用户人工查看空列表及点击导入，结果按实际反馈记录。已有资料完整承接候选时 no-new-learning，不造经验条目。允许的知识补充由 Lead 统一合并。所有角色终态后交付改动、验证和待验；本地 commit、push、版本、Release 分别按明确授权。复杂交付可用表格，简单单包不强制三栏目和两表。
