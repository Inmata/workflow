# 公共工作方法

项目首次明确接入后，Lead 读取本文件和[Lead 指引](roles/lead.md)。实施工作包只附本文件、[Worker 指引](roles/worker.md)和直接项目资料；审查工作包改附[Reviewer 指引](roles/reviewer.md)。验证或实际失败时读[验证约定](references/validation.md)，需要复杂交付时读[报告约定](references/reports.md)，Codeg 交接或接续时读[适配说明](adapters/codeg.md)。

Lead、Worker、Reviewer 按职责分配，依据用户已确认的安排、当前可用工具和任务需要选择智能体；不按客户端或模型名称固定角色。主会话承担 Lead，受委派会话按工作包承担 Worker 或 Reviewer；同一种智能体可在独立会话中承担不同角色。hook 安装参数只选择宿主接入方式，自动接入的支持范围见 [README](../README.md#角色与接入支持)。

## 项目对齐

首次进入已接入项目，Lead 先按[项目对齐协议](alignment.md)做一次只读对齐，结论写入项目 `docs/WORKFLOW-ALIGNMENT.md`。项目现有做法与 workflow 默认不同的地方逐条交给用户裁决：不默认项目优先，也不默认插件优先；证据表明项目做法过时（例如文档版本号与代码常量不一致）时在建议中指出，但仍由用户决定是否改项目。文档过期、重复、缺索引或链接失效只列入结构建议，用户批准后才在后续任务修改。

之后会话开始和每个用户回合只做增量检查：索引文件的大小、mtime 或所在目录变化时才重读，不因一个文件重扫整个项目；新增资料由目录变化提示，下次 `project align scan` 补入。对齐保持 operation-only，不派 Worker、不进入实施。

## 分流

先核对当前用户目标、项目现有入口、直接相关实现和验收。已有确认计划直接沿用；只做计划的请求停在方案，不实施。能从仓库和工具确认的信息先查；真实缺失的需求、权限、接口或负责人整理成具体问题，已有独立工作继续。

查看状态、推送指定提交、目标明确且无冲突的快进拉取，默认零 Worker、零 Reviewer，声明 operation-only。保留未提交内容；不自动 add/commit、不补开发、不初始化空资料。出现分叉、冲突或实际代码修复时，只重估受影响范围。

低风险单点修改允许 Lead 实施。关键行为即使只改一行，也需必要独立审查。复杂任务按业务依赖、未知因素、所有权、验证和协调成本决定人数；不默认两名 Worker，不为并发强拆，不按 UI/后端或文件数均分。同文件和同一状态机唯一负责人，worktree 不解除业务耦合。需要独立角色而实际入口不可用时如实记录 BLOCKED，生成交接文本只表示准备完成。

多人链条为：目标/验收 → 实施/自测 → 独立审查 → 定向返修/复审 → 集成/必要回归 → 人工验收 → 已授权的提交/发布。已满足或不适用的步骤说明原因后跳过。角色与并发上限沿用用户已明确的项目或阶段安排；确需新增、更换或缺少角色时再补齐决定。子角色不加载 Lead 调度流程、不递归创建代理。

## 边界

所有用户可见说明使用简体中文；代码、命令、路径和必要原文保留。每阶段简短说明目标和最小读取范围，范围变化时再说明。读取、搜索、验证针对当前问题，入口未知先最小定位；不扫描无关目录、旧快照、其他 worktree、无关插件和个人库。问题已有证据结论时直接推进；只有新失败、需求变化或具体新证据才重开调查。

全局规则与本方法发生具体冲突时，只依据当前已加载规则报告具体条款；涉及安全底线或用户意图交用户，其余范围、播报和审查冲突交 Lead 裁定。协作需要 workflow 身份而当前没有时停止寻找，不搜索其他会话或全局配置、不推算票据。

当前明确用户要求优先。修改、修复、安装、配置或生成的明确意图授权必要可逆写入；讨论、分析、检查保持只读。常规步骤自主执行，授权或任务边界不清再提出具体问题。编辑前先读原文，保留用户未提交内容。重要配置/核心文件修改前在项目 backups/ 保存非敏感必要备份；没有项目根则明确备份位置。

删除/清理使用可靠回收站；没有回收能力则保留并报告，不永久删除。修改或移动软/硬链接、符号链接、Junction 前核对类型、真实目标和影响范围。凭据只引用环境变量名，不查看、输出、备份或传播真实值。发现敏感内容时停止扩散，只说明受影响位置。

复杂实现交付前做独立只读审查，范围限交付物和直接依赖；简单配置/单点文本可免。方便用户观察的界面交用户验收；难稳定验证的逻辑做必要自动检查。已有有效证据直接复用，不为更保险、换审查人或查看标签重复全测。结论分别标记完成、自动验证、真实宿主验证、人工验收、推断和未知；未运行、未进入目标场景、交接未送达均不能写通过。

接口达到验收并经用户确认后冻结；已知小限制留后续，由用户决定是否追加。不把新功能塞进返修收尾。提交、push、版本与 Release 分别按授权执行，本地检查点也不例外；人工验收不自动授权发布。保留当前原技能和规则的可恢复来源，试点迁移按项目选择一套活跃入口。

## 知识

Worker 随正常交付回报稳定 ID、事件 ID、适用条件、发现和证据；Reviewer 随正常审查核对事实、反例及过时条件。Lead 按[经验学习](learning.md)将值得保留的短材料写入本机 inbox，后台在额度与权限内整理。简单任务由 Lead 完成；不为经验另开角色或强制造条目。

项目事实优先放已有 README、spec、实现说明和计划，保持名称和路径；当前任务确有缺口才补写。明确区分批准需求、草案、预期、当前实现和进度：spec 要求 500、实现 100，记录差距，不能把要求改成 100 或宣称 500 已实现。未集成分支的事实附分支/版本条件。项目资料缺失可接入，不创建空 LESSONS、空架构目录或必填文档套件。

任务开始或范围变化时先检索适用经验，区分成熟度、重要性与状态；高重要性不代表已验证，也不能越过当前用户要求。明确纠正或已验证失败引用旧知识 ID，立即停止默认召回，后台再判断条件差异、修订或替代。保留证据、原因和版本；新结论不继承旧结论的成功等级。没有新材料无需触发学习。

项目知识可自动维护，长期偏好、公共方法和权限边界仍由用户决定；频次不能晋升权限。聊天原文不搬入经验，能由配置查到的事实链接来源，进度回原计划。document-learning 独立管理个人文档经验；按用途而非 .md 后缀划分，不复制同项正文或消费对方信号。

当前业务所需的共享资料写入使用 knowledge inspect/apply。只写当前任务 allowedPaths、真实项目、明确知识负责人和有效 write 身份；旧指纹、用户编辑、链接、锁竞争返回冲突/待办。多文件可部分成功，同一候选全部目标完成才算完成。后台只获 `.workflow/knowledge/` 的独立维护权限，活动、只读或计划任务期间延后。旧 disposition 保留兼容，但不再是交付条件。

## 提问路径

需要用户裁决时按以下顺序选可用入口，不要求用户切换模式，插件也不切换模式：

1. 宿主原生结构化提问（Codex `request_user_input`，Claude Code `AskUserQuestion`），当前模式可用时；
2. Codeg MCP `ask_user_question`，与宿主模式无关；
3. 普通文本编号问题。

三种都先声明 waiting-user。插件能识别前两种工具调用；文本提问由 Lead 显式发 phase 信号，插件不读问号或关键词猜测。每次最多 4 个问题，对应工具上限。可持久保存的待决项（如对齐表格）允许跨回合回答。各宿主各模式下的可用工具见[Codeg 适配](adapters/codeg.md#宿主能力表)。

## 收尾

按[协议](design/protocol.md)声明 task-start（附 `route`：`operation-only`、`lead-direct` 或 `delegated`）和明确阶段；提问先 waiting-user，完成后 task-end。分工任务只在三个节点用一次批量 `packages` 信号记账：派发、消费结果、审查结论；不记录等待过程。`delegated` 任务的 task-end 核对：全部包为终态，每个 worker 包有 `verdict=PASS` 且 `reviewedRef` 等于其最终 `deliveredRef` 的 reviewer 包，验证记录 `validation.ref` 等于集成后版本；父任务还不能有活动子任务。缺项返回 `GATE` 与 `missing`，状态不变；确不适用的步骤用 `waivers:[{step, reason}]` 显式豁免并留记录。门禁核对的是 Lead 声明记录的一致性，不证明审查或测试真实发生；`lead-direct`、`operation-only` 不设门禁，关键行为一行也要审仍由 Lead 判断。Stop 不阻断知识处置、不追加复盘轮次。用户中断时撤销票据、挂起业务任务并释放会话归属，下次显式 task-start 才恢复。待办按事务独立保存，其他事务成功不能将它清除。复盘的时间、批次与每日限额见[经验学习](learning.md)，业务停止限制见[验证约定](references/validation.md#停止限制)。
