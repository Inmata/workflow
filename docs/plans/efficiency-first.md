# workflow 效率优先改造计划

状态：待实施。当前只完成调查与计划整理，未授权按本计划修改产品代码。

日期：2026-10-27。调查基线：0.6.2，提交 `b2799d8`。

## 1. 首要目标与取舍

用户明确要求：

> 效率是一切的核心，质量都得在它后边。

本计划据此排序：**完成用户目标的效率第一，质量提升第二，架构整洁与规则完整性排在其后。** 效率包含用户等待时间、模型消耗、人工操作、协调往返，以及交付后的实际返工。不能只减少本轮调用、把明显未完成的工作转嫁给用户，也不能以“以后可能返工”为理由无限增加检查。

具体决策原则：

1. 默认采用能完成任务的最短路径。简单任务直接完成，不为流程完整安排角色、生成文档、创建快照或补齐不适用的表单。
2. 每个额外环节必须对应一个具体问题，并说明其收益为何值得当前成本；缺少依据时先省略或做最小检查，不默认升级成全面审查。
3. 接受不影响当前目标的小限制和已说明的不确定性。达到验收就结束，不追求零疑点、零技术债或无限完善。
4. 用户已经给出的授权、角色安排和验收直接沿用，不重复确认。只对真实新增的边界或决策提问。
5. 保持如实报告、用户授权与数据保护。这些约束不作为增加形式化质量流程的理由，也不因追求速度而伪造完成、测试或审批。
6. 每批改造必须能独立带来收益。后续批次没有足够收益就停止，不为了完成本计划而把所有条目做完。

本次不实施代码、不重装第二次、不提交或推送。后续开始实施时另建工作分支；版本号在实际发布范围确定后再定。

## 4. 目标工作方式

### 4.1 简单任务

理解目标 → 必要修改 → 最小相关验证 → 交付。

允许 Lead 直接完成；不创建工作包、快照和独立审查会话。已有任务生命周期暂保留，但开始和结束各一次调用。纯查询与明确操作继续走 operation-only，不附加审查或验证账本。

是否独立审查按具体行为及失败代价判断，不按文件数、一行代码、目录变化等单一标签机械触发。涉及核心状态写入、并发身份或不可逆后果时，可以有一次集中审查；审查范围仍限实际变化。

### 4.2 需要协作的任务

明确工作包 → 委派 → 消费产物 → 必要独立审查 → 集成与相关验证 → 交付。

- 不把 1 个负责人能高效完成的工作强拆为多个包。
- 保留派发、消费、审查结论三个记账节点；同次消费与下一阶段派发合并。
- Worker/Reviewer 不维护 Lead 账本；独立会话一次角色绑定，内置子代理直接按工作包工作。
- 工具返回完成只证明子任务结束，不自动等同于 Lead 已消费，更不等同于审查 PASS。
- 返修只处理具体缺陷与直接影响，复用仍适用的结果，不从头重做调查和验证。
- 达到目标即结束；未完成但继续成本已不值得时，如实说明剩余项，不伪装完成或无限循环。

### 4.3 等待与反馈

内置子代理使用宿主完成通知。Codeg 在当前工具仍需等待收取结果时，使用一次批量阻塞等待（`wait_ms: 0`；遇 `blocked_on` 会提前返回，MCP 空闲超时断开而任务未中断时直接重调续等），不再按 60s 间隔轮询涨上下文；终态任务消费后移出集合。实际工具能力变化时更新对应适配，不在公共规则里写死所有宿主的行为。

反馈检查发生在派发前、重要决定前、消费结果后及超时重连间隙（宿主本身已能在阻塞调用期间打断并送达用户消息的，如 Claude Code，无需为读取反馈定时唤醒）。不要在连续没有实质进展的短步骤或等待期间机械插入检查或无关命令。

## 5. 第一批：规则减负与一次调用信号

这是首个可独立交付的范围。完成后即可试用，第二批不是前置条件。

### A1. 收敛规则与按需入口

涉及：`src/context.mjs`、`docs/workflow.md`、`docs/roles/lead.md`、`docs/roles/worker.md`、`docs/roles/reviewer.md`、`docs/adapters/codeg.md`、Claude 适配文档。

实施内容：

1. 公共入口保留目标、授权、如实报告、最少流程及结束条件。Lead 细则按协作、spec、UI、诊断等场景导航；简单任务不要求先读全部细则。
2. 协议字段只在协议文档权威定义，角色指引只说明何时调用和需要做出的业务判断。
3. 首次进入、角色或版本变化、压缩恢复时给必要完整入口；普通用户回合给当前身份、任务变化、待处理事项与相关导航。身份变化照常发送，固定长指令不反复发送。
4. 判断无法确定是否已加载时回退到短完整入口，不能因“去重”导致恢复后没有必要规则。
5. `compactLedger` 仅补恢复所需的 channel 与 supersededBy；不附工作包正文、完整日志或全部历史结果。
6. 将“必须先批准才能做每一次补测”等固定往返，改为包内事先授权的验证范围。范围内必要定向检查直接执行，超范围或有外部影响再交 Lead。
7. 整体结构检查仅在存在实际边界或集成风险时并入既有审查，不因新增目录等机械条件固定再开一个 Reviewer。

验证：使用精简的 context fixture 检查普通回合、角色变化和压缩恢复；核对文档导航和等待说明。无需为文案长度逐句写测试。

验收：

- 简单任务首次必读内容目标不超过基线的 50%（约 5,331 字符）；以本批完成时同口径测量为准。
- 普通回合不重复发送完整固定指令；不以隐藏到另一份默认必读文档的方式满足目标。
- 对无变化、无在途事项的回合，只有完成当前动作所需的信息。
- 上述字符目标是减负方向，不能为达标损坏恢复语义；少量超出时说明实际取舍，不继续进行无收益微调。

### A2. 一次调用的信号接口

涉及：`bin/workflow.mjs`、`src/hooks.mjs`、`src/protocol.mjs`、`src/context.mjs`、信号相关测试及使用说明。

建议接口方向：继续使用 signal 入口，提供常用动作的结构化参数；常用的 task-start、task-end、phase、role-claim 不要求临时 JSON 文件。复杂 packages 保留 `--input`；需要多项长文本时不强行塞入 shell。

示意（参数名在实施时统一，不代表现有命令已经支持）：

```text
workflow signal task-start --context <回合句柄> --request <请求ID> --task <任务ID> --route lead-direct --mode write --goal <目标>
workflow signal task-end --context <回合句柄> --request <请求ID> --task <任务ID>
workflow signal packages --context <回合句柄> --request <请求ID> --input <业务字段JSON>
```

执行机制：

1. hook 注入绑定项目、session、turn、epoch 的紧凑上下文句柄。优先从可信宿主字段建立绑定，不按项目的“最近会话”猜身份。
2. CLI 只读当前绑定并补齐协议字段，生成规范信号；仍由当前调用的 PostToolUse 验证并应用，不在 CLI 和 hook 各写一次状态。
3. 不接受从任意文件输出中捞到的信号；直接调用识别保持明确。身份、项目、回合在 hook 处再次核对。
4. CLI 读取时取得 revision，hook 应用前有并发变化就拒绝；不在应用时强行改成最新 revision。过期回合句柄直接失效，不自动转绑。
5. 相同请求在原有效回合重试时复用已生成的规范载荷或已接受回执，不能因重新补 revision 导致正文漂移。请求业务内容改变仍报冲突。
6. 请求标识可由宿主稳定调用标识或入口给出的短标识提供；无可靠来源时保留一个显式短 request ID，优先实现正确且短的接口，不为彻底零字段扩建服务。
7. 多个状态修改按顺序发送；只读调查可以并行。不通过自动无限重试隐藏冲突。
8. 报错只返回具体缺项、可恢复状态和下一步，不重复整份协议。内置子代理发信号时只说明无独立身份，直接交回工作结果。
9. 保留旧 `signal --input/--base64` 和 v1 载荷兼容，新的便捷入口转换到同一状态机，不维护两套门禁。

实施前限一次小探针，验证当前两种宿主能否可靠提供会话/回合绑定以及短参数的直接调用回执。若需要持久化请求规范载荷，只新增最小本机记录，并明确旧状态缺省值；不静默覆盖旧格式。无法可靠绑定时保留显式句柄，不能降级为全局最新身份。

测试只覆盖关键行为：并发不同 session、过期 turn/epoch、读取与应用之间 revision 变化、同请求重放/改正文、旧接口、原子失败回滚，以及两个宿主的直接调用识别。复用现有 fixture，不创建全套新的测试框架。

验收：

- lead-direct 开始与结束合计从 4 次协议工具调用降为 2 次。
- 每次信号不再复制整组身份字段；常用动作无需生成临时文件。
- 复杂 payload 使用文件时如实计算两次调用，不宣称所有协作任务已减半。
- 原无返修协作样本的 10→5 次是后续便捷批量载荷的优化目标；第一批若只能做到部分减少，记录实际值，不为达成数字扩大接口范围。

### A3. 第一批结束点

完成 A1、A2 后跑相关测试；集成结束运行一次仓库要求的 `npm test` 与 `npm run check`。围绕身份与状态写入安排一次集中只读审查，不为文档、CLI、hook 各开一个审查链。已通过的测试仅在后续修改影响结果时重跑。

## 6. 第二批：产物引用与快照辅助

启动条件：第一批已经获得实际减负；任务确实需要审查未提交内容或频繁手工对齐版本。无该需求时延期。

涉及：新增小型产物引用模块（建议 `src/artifacts.mjs`），以及 `bin/workflow.mjs`、`src/protocol.mjs`、`src/spec.mjs`、角色交付模板和对应测试。

### B1. 统一“审的是什么”

- 已有提交：复用解析后的完整 commit OID，不再人工创建额外检查点。
- 未提交内容：按显式允许范围生成不可变清单，记录基线、相对路径、内容摘要、删除项及必要文件模式。引用可解析到冻结内容。
- 引用类型明确区分 commit 与 snapshot。旧字符串保留兼容并标为旧声明记录；不能伪装成已校验的内容引用。
- Worker 交付、Reviewer 结果和验证记录复用同一产物引用；后续内容改变，旧结果的适用范围需要重新判断。
- 自动关联只能证明内容对象一致。测试证据仍需真实执行输出，审查结论仍来自 Reviewer，不自动推断 PASS。

### B2. 快照命令边界

1. 只在需要冻结未提交产物时调用，普通小改不强制。
2. 默认不 commit、不移动分支、不改用户 index、不 stash、不清理文件。采用独立内容存储，避免为了快照制造 Git 历史。
3. 允许范围由任务给出；不使用全仓 `git add -A`。无关未跟踪文件、忽略文件和用户不属于本任务的修改不隐式纳入。
4. 显式处理删除、二进制和链接；不支持的类型明确报告，不遗漏后仍宣称完整快照。
5. 读取前后内容不一致或工作区持续变化时报告无法形成一致快照，要求负责人暂时停止修改；不无限重试。
6. 快照写入失败不能更新交付状态。创建和后续引用有稳定 ID，可恢复，不自动清理历史。

### B3. 与 spec、集成验证的关系

当前 `finalRef` 被传给 Git spec 检查。引入 snapshot 后必须明确分路：提交引用继续按提交检查；快照使用其基线和冻结文件内容判断相关漂移。不能把 snapshot ID 直接当 Git ref，也不能静默回退到 HEAD 后宣称检查了快照。

为控制范围，可以先交付“包级审查快照”：支持 Worker/Reviewer 对齐，最终 task-end 仍使用现有提交或工作区 spec 检查，明确两者证据对象。完整快照 spec 支持只有在实际任务需要时再做，不作为前一批减负的阻塞项。

验收场景：已有提交无需新快照；未提交文件变化能识别旧引用；用户 index 和分支不变；无关文件不纳入；删除项可还原审查范围；不支持的最终快照检查明确报告；旧载荷继续可用。仅对这些边界做定向测试和一次相关审查。

## 7. 第三批：局部运行开销

启动条件：操作往返已减少，仍有可感知 hook 延迟，或测量显示这部分值得优化。

涉及：`bin/workflow.mjs`、`src/hooks.mjs`、`src/store.mjs`；必要时再触及 `src/install.mjs`、`src/projects.mjs`、`src/spec.mjs`。

1. 分开测普通 PostToolUse、入口上下文、signal 和 Stop，固定环境重复少量运行，记录样本数与中位数，不混成一个“hook 耗时”。
2. 在同一锁作用域内复用已读取的状态原文与解析结果，减少无意义双读；保留锁内重新核对需要的并发语义。
3. 让持久化结果可判断是否有未保存修改，消除 Stop 同状态重复写；保证返回继续决定前预算已落盘。
4. 安装和知识事务中用于恢复的中间 save 保持语义，不能用“每次只写一次”机械替换。
5. 只有测得静态模块加载占明显成本时，才对 CLI 做按命令延迟加载；不为分层而拆全部模块。
6. 不把内容校验替换成 size/mtime，不靠自动删除 receipts 或全局放宽锁提升速度。若未来调整完整性策略，单列收益与语义变化后再决定。

验收：相关路径时延或 I/O 次数可复现地下降，且迁移备份、故障回滚和持久化顺序保持正确。没有明显收益则停止该批，不继续为毫秒追求架构重写。

## 8. 验证收益的最小办法

不开发统计平台，不常驻调用额外模型，不向每个任务增加汇报表。

使用三个固定场景：简单修改；单 Worker 加独立审查；一次定向返修。先用现有记录或可重现 fixture 建立旧基线，再在改造后跑一次相同定义的流程。无需为了对照把所有真实业务再做一遍。

仅记录：

| 项目 | 口径 |
| --- | --- |
| 协议调用 | 写载荷、发信号、补身份、读账本及其重试；与派工和业务工具分开 |
| 等待 | 阻塞等待次数与可获取的等待时长；不把长等待直接视为浪费 |
| 重复工作 | 已消费结果重读、无新依据的重复全测、反复加载同一规则 |
| 模型使用量 | 只用宿主真实 usage；区分缓存与非缓存，避免重复累加流式或累计字段；没有则留空 |
| 交付结果 | 用户目标是否完成，有无实际漏项、错误产物或新增返工；不以账本闭合作为质量证明 |

工具调用不等于模型轮次；字符数不等于 token；token 不等于账单；消息间隔不等于有效工作时间。不把不同复杂度任务的绝对耗时直接比较。

判定规则：调用与重复工作下降、交付目标完成，即认可该批减负。没有发现缺陷只表示当前样本未暴露问题，不启动更大质量工程。若少量抽样显示新流程反而更费时，先撤回新增步骤或缩小适用范围，不通过追加更多规则修补其负担。

## 9. 实施边界、迁移与停止条件

- 不新建通用框架。宿主适配负责身份和事件；现有 protocol 负责状态转换；确需时新增小型产物模块。旧入口与新入口共享同一实现。
- 规则文档、上下文提示和实际行为在同一批同步。新增规则时明确它替代了哪些重复规则，不只追加段落。
- 不强制立即迁移所有旧任务，不重写历史 receipts，不给旧声明补造真实证据。
- 若确需变更状态 schema，遵循现有迁移备份和未知版本拒写机制；能用可选字段兼容则不为统一格式额外迁移。
- 每批可单独停止、延期或回退；出现跨会话串写、用户内容意外纳入快照或无法确定交付对象时停止受影响路径，其他减负部分不连带取消。
- 研究限于能影响当前决策的证据。确定原始样本不在已知记录位置后停止扩搜；缺数据直接记未知。
- 实施每批先给出具体改动范围，沿用用户随后给出的执行授权；不逐文件、逐测试重复审批。
- 不因本计划建立额外 CI 平台、定时评估或永久观测设施。

## 10. spec 与文档影响

本仓库当前没有 `.spec`。本计划不为自身引入 spec 体系，spec 影响为“无”。第二批如修改产品对用户项目 spec 的处理，须同步对应使用说明和测试，但不把尚未实现行为写成现状。

需要随相应实现更新：`docs/workflow.md`、角色指引、`docs/design/protocol.md`、`docs/usage.md`、宿主适配、相关 README 和命令帮助。第一批只更新第一批实际行为；后续草案留在本计划。

`0.6.2.md` 保留历史完成记录，并链接本计划承接原后续，不把原版本改写成已经具备新功能。
