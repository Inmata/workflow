# 0.7.0 → 0.8.0 耗时实测

测量日期：2026-10-30。结论：普通入口和无 spec 收尾没有稳定的提速证据；小型 spec 项目的正常收尾增加约 65–73 ms。新版主要减少慢 Git 对其他会话的阻塞，并缩短 Git 卡住时等待拒绝回执的时间。

## 比较对象

| 对象 | 固定标识 | 说明 |
| --- | --- | --- |
| 正式 0.7.0 | Git 标签 `v0.7.0`，提交 `22f86cf6cd44c6e55ba74534a128ab113994dc28` | 通过 git archive 导出的正式发布基线 |
| 测量前本机 0.7.0 | 安装摘要 `cd2f4b5b7f28e479204c40546f304c30f197f99e70ceec42e164bdb6ea8d7c81` | 后续重装的同版本新摘要；18 个 src/*.mjs 与当前源码逐字节一致 |
| 源码 0.8.0 | `5eddd1e162c9fe7fc0795e5b9e1dd481f72b9ce0` | 测量时 main 的源码；本次新增的基准脚本不进入安装发布白名单 |

“本机仍为 0.7.0”描述的是版本登记，不能据此认定本机尚无锁外预检等修复。本机已经包含这些运行代码；重装 0.8.0 主要对齐版本、产品文档和安装记录，不能承诺再获得同一批修复的性能收益。

## 方法与证据边界

- 同一台 Windows 11 机器，Node.js v24.21.0、Git 2.55.0.windows.5。默认系统负载，没有清空操作系统文件缓存。
- 借鉴现有 `scripts/bench/compare.mjs`、`test/helpers.mjs` 和 F05 慢 Git 测试；每个样本建立独立项目、状态和 47 文件的发布副本，不读取真实宿主配置。
- 普通场景每版每场景 9 次，三版运行顺序逐轮反转；没有专门丢弃预热轮。报告中位数和原始范围。中位数基于混合缓存状态，不是冷启动保证。
- 被计时的是完整真实 CLI Hook 子进程，包含 Node 启动、项目辨认、适用时的发布完整性校验和状态落盘；夹具建立、Git 初始化和文件复制均在计时外。
- 使用合成 Codex 事件，没有调用模型，也不是实际宿主调度耗时。posttool 是普通 Edit 的快速放行路径；Stop 场景使用活动任务，因此预期结果是要求 task-end 的 block；task-end 正常场景必须收到 accepted 回执。
- spec 项目只有一个 spec、一个受管小文件和一个种子提交。没有覆盖大仓库、长历史、多 spec、知识召回规模变化或多个模型会话的端到端延迟。
- 延迟注入只拦截 spec 的 `--literal-pathspecs` Git 调用。慢样本在每次调用前等待 350 ms 后执行真实 Git；该人工等待没有从传给 spawnSync 的 timeout 中扣除，不能用于验证严格的绝对超时保证。卡住样本按照调用者 timeout 等待后返回模拟 ETIMEDOUT，不是启动真实挂死的 Git。
- 竞争者在首次 spec Git 调用开始后启动独立 Node 进程，用对应版本 withLock 尝试获取状态锁，预算 1200 ms。表中的竞争等待从进程内申请锁开始计时，不含竞争者 Node 启动；Hook 总耗时包含它自身启动。
- 所有夹具保留，未执行物理删除。本次测量工作目录整体移至 `backups/benchmark-080-20261030-local/bench-080`，避免进入对齐扫描和提交。脚本不会自动清理；需要清理时统一使用终端 trash。

## 正常场景

单位 ms。括号为最小值–最大值；每格 9 个有效样本。

| 场景 | 正式 0.7.0 | 本机 0.7.0 新摘要 | 源码 0.8.0 | 0.8.0 相对正式版 |
| --- | ---: | ---: | ---: | ---: |
| 用户输入入口 | 232.6（228.7–265.6） | 234.7（223.6–279.5） | 232.3（229.4–273.6） | -0.1% |
| 普通 Edit 后 Hook | 126.6（120.4–161.9） | 127.1（120.4–175.7） | 125.1（120.6–133.4） | -1.2% |
| Stop，无 spec | 226.0（220.7–278.9） | 226.9（218.5–304.2） | 228.5（221.8–244.0） | +1.1% |
| task-end，无 spec | 228.3（223.2–291.8） | 262.6（223.7–294.1） | 224.7（220.3–298.6） | -1.6% |
| Stop，有 spec | 651.0（600.6–706.0） | 714.2（674.3–834.1） | 716.1（673.0–903.8） | +10.0% |

全部 162 个正常样本符合预期。不同时间段会出现系统抖动，尤其本机与源码版运行代码完全一致，其差值不能解释为代码优化。新版有 spec 路径增加绑定快照与 ref 复核；本次结果与这些额外检查的开销相符，但未单独剖析各检查耗时。

## 慢 Git 与竞争

| 场景 | 正式 0.7.0 | 本机新摘要 | 源码 0.8.0 |
| --- | ---: | ---: | ---: |
| 每次 Git 注入 350 ms：task-end 总耗时中位数，3 次 | 2821.8 | 3289.1 | 3206.9 |
| 同时申请锁：成功次数 / 3 | 0/3 | 3/3 | 3/3 |
| 竞争者等待中位数 | 1208.5，LOCKED | 6.1，成功 | 6.2，成功 |
| Git 注入超时：返回拒绝回执，1 次 | 10280.1 | 4234.4 | 4241.8 |
| 超时场景竞争者 | 1206.2，LOCKED | 6.0，成功 | 6.5，成功 |

350 ms 场景三版均 3/3 接受 task-end；0.8.0 自身总耗时比正式版增加约 385 ms（13.6%），其收益是释放状态锁让其他会话工作。超时场景三版均返回 GATE 拒绝，未把未完成检查当成通过；0.8.0 约少等 6038 ms（58.7%）。超时只有每版 1 次诊断样本，不报告分位数或稳定成功率。正式版本次返回超过配置中的 10 秒宿主窗口，实际宿主可能先终止它；本测量未模拟宿主强杀。

4 秒是从检查开始计算、供预检 Git 调用共享的截止预算。同步文件快照不可强制中断，也会消耗预算；锁内 ref 复核有独立预算。因此不能称为整个 Hook 或预检的严格 4 秒上限。

## 0.8.0 的用户影响

| 改动 | 使用者会看到什么 |
| --- | --- |
| 新任务必须明确 route | 缺失或非法 route 会拒绝，避免新任务绕过应有分工门禁；已有历史任务仍有兼容路径 |
| spec 锁外预检、快照绑定和有界复核 | 慢 Git 不再长时间占用状态锁；期间代码、提交或索引变化会拒绝旧报告，要求重新检查 |
| 接入先完成核心预检 | 核心接入失败时，不提前调用项目或个人配置的执行器 |
| PowerShell 参数按字面传递 | 特殊路径、美元符号和引号不被意外展开；兼容传输须由明确开关启用 |
| 对齐读取故障可见 | 读取错误会显示 errors 并标记 stale/incomplete，避免静默视为没有资料 |
| 未应用的对齐事务保持 pending 可见 | 后续入口能提示待恢复事务 |
| npm run verify | 维护者可组合现有检查并保留日志、summary；不改变用户项目的测试要求 |
| 回滚职责与模块引用说明 | 明确直接调用协议时的事务责任；生产 Hook 已有的整体回滚继续保留 |

知识缓存没有改成每次全量读内容；等长且保留 mtime 的改写边界仍保留，不属于本次提速。

## 复现与产物

脚本：[version-080.mjs](../../scripts/bench/version-080.mjs)、[慢 Git 注入](../../scripts/bench/version-080-slow-git.mjs)。原始数据：[version-080-benchmark.json](version-080-benchmark.json)，共 174 个样本（162 正常、9 慢 Git、3 超时）。探索夹具与交付脚本的额外 smoke 不混入统计。

在仓库根目录准备新的空 `.local/bench-080/baseline`，用 `git archive v0.7.0` 导出到该目录。运行：

```powershell
node scripts/bench/version-080.mjs batch 0 3
node scripts/bench/version-080.mjs batch 3 6
node scripts/bench/version-080.mjs batch 6 9
```

最后一批同时运行慢 Git 和超时场景。三个批次分别写 raw-0-3.json、raw-3-6.json、raw-6-9.json，须合并后统计。可通过 WORKFLOW_BENCH_AREA、WORKFLOW_BENCH_BASELINE、WORKFLOW_BENCH_INSTALLED、WORKFLOW_BENCH_SOURCE 环境变量指定路径；环境不含 LOCALAPPDATA 时必须显式指定安装副本路径。重装后默认 installed 路径代表新版；要复现旧本机样本，应明确指定保留的 `releases/0.7.0-cd2f4b5b7f28e479`。

测量时 GitHub 最新 Release 是 [v0.7.0](https://github.com/Inmata/workflow/releases/tag/v0.7.0)，没有 v0.8.0 标签或 Release。本次基准不能由历史 0.6.3 → 0.7.0 报告替代。测量后已将 Claude Code 与 Codex 重装为 0.8.0，共用摘要 `b4ea11743fb29971d13c9916500ca6661cba9473210cd7be3a3f1533fff78df8`。两宿主 doctor 均为 registration=registered、integrity=verified；trust/discovery=unknown。旧发布副本保留，安装器拟删除的旧入口链接通过运行时适配改名保留，没有物理删除。当前 Claude 会话在升级后已收到 task-start 的 accepted 回执；独立新会话和 Codex 升级后真实回调未验证。截至测量与安装完成时，0.8.0 尚未公开发布；当前发布状态以 GitHub Release 为准。

## 发现的文档与代码不一致

- `src/spec.mjs` 的 budgetMs 注释称其限制“整次检查的总时长”“保证在宿主回执窗口内返回”，比实际实现更强。实际受约束的是带 deadline 的 Git 调用；同步快照不可中断，锁内复核另计预算。当前 README 的说明更准确。本次未修改产品代码。
- 旧效率报告所引用的 `scripts/bench/compare.mjs` 实际仍在仓库中，早期宽泛文件名匹配漏查；这属于本次定位错误，不是报告引用缺失。
- “源码 0.8.0、本机 0.7.0”与版本文件一致，但不足以表达运行源码已一致的事实；本报告补充了摘要和逐文件比较，不能把版本差异当作性能差异。
