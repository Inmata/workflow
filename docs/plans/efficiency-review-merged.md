# 两轮全仓审查合并计划：减少等待、往返与恢复成本

状态：计划待实施。本文件仅合并审查、确定建议范围与验收；没有实施以下产品改动。

日期：2026-10-28。代码基线：0.6.3，`2721bcc`。本计划承接[上一阶段效率改造](efficiency-first.md)，不重新实施其中已完成的三批工作。

## 1. 目标、依据与执行边界

效率第一，质量排在其后。优先减少真实用户等待、模型调用、上下文增长、重复审批和人工恢复；验证只服务于避免具体返工，不为了清零疑点扩建流程。

合并依据是两轮主会话与 Codex 全仓审查。第一轮提出 13 项；第二轮逐项校正，并用临时 fixture、内存状态和假 runner 复现新增边界。此处按实际原因去重，不把两轮票数当严重性证明。第一轮部分判断和建议撤回，详见第 3 节。

已具备的基线证据：第二轮 `npm test` 为 146/146 通过，`npm run check` 为 0 错误（38 个语法文件、25 份文档、47 个发布文件、134 个本地链接）。这些通过结果不覆盖全部新发现，也不代表问题已经修复。本计划整理不重跑全套行为测试。

当前授权仅为整理计划。后续实施时：

- 从届时工作区建立工作分支，先核对基线与已有改动；不把 `.local/` 纳入任务。
- 不读取或手改真实宿主全局配置，不读取其他会话凭据，不用真实默认状态制造故障。
- 提交、推送、版本、tag、发布、真实宿主重装按各自明确授权执行；本计划不隐含这些授权。
- 不熟悉的锁恢复、持久事件或调度实现，在对应包动手前限一次有针对性的 GitHub 开源实现对照；只解决尚未确定的机制，不再重做全仓调查。
- 建议不增加第三方运行时依赖，不引入通用事件总线、数据库迁移工程或统计平台。某项最小修正开始膨胀时先缩范围并报告。

## 2. 保留的能力与优先级

已有减负继续沿用：常用 signal 一次调用、短角色入口、非默认分支本地检查点 commit、Codeg 批量阻塞等待、同状态 Stop 不重复保存、普通 PostToolUse 早退。未出现新失效证据时不重写。

以下边界继续保留：

1. 分包、角色与通道在计划中一次说明；已有用户安排直接沿用，缺失且确实需要时才提问。
2. Codeg 等待使用批量 `wait_ms: 0`；终态消费后移出等待集合。工具断开而任务仍在运行时续等，不短间隔轮询。
3. 已审 worker 包不能靠 waiver/waived 绕过最终交付版本审查；变化很小时可做针对新增差异的复审，不必重新全仓审查。
4. 知识和对齐写入保留指纹冲突检查、事务恢复、链接目标检查与用户未提交内容保护。
5. `task-end` 仍是明确完成声明。门禁无缺项不证明业务完成，Stop 不自动替 Lead 结项。
6. 不盲目继承上一回合的 waiting-user；用户回复会开启新回合，需要重新判断当前状态。

优先级按消除实际返工和人工介入排序：

| 阶段 | 范围 | 首要收益 | 结束点 |
| --- | --- | --- | --- |
| A | P01–P03：生命周期、可选上下文、后台接续 | 避免丢状态、任务被误挂起和正常竞争转人工恢复 | 核心并发场景恢复，无新增模型调用 |
| B | P04–P05：对齐与检查对象 | 避免同一变化反复对齐，以及错误版本导致的误拦/漏检 | 已确认变化能收尾，检查对应真实 worktree/ref |
| C | P06–P08：接入、权限变更、返修计数 | 消除修复入口失效、权限升级绕路与虚假返修 | 对应问题各有直接出口 |
| D | P09–P11：规则、CLI、测量后优化 | 减少重复确认、临时输入和无效扫描 | 低成本减法落地；无收益性能项可停止 |

A、B 优先。每阶段可独立交付；C、D 不成为前两阶段交付前置条件。收益不承诺百分比，不按条目数量认定成功。

## 4. 阶段 A：减少状态丢失与人工恢复

### P01 生命周期竞争、任务归属与恢复锁

依据：已复现入口争用导致新 session 未持久化；Interrupt/SessionEnd 争用导致任务仍 active；两个 session 共用 task 时任一结束会挂起另一方；注入残留 `.recovery` 后连续请求仍 LOCKED。最后一项模拟的是残留状态，尚未验证精确进程崩溃窗口。

涉及：[store](../../src/store.mjs)、[hooks](../../src/hooks.mjs)、[protocol](../../src/protocol.mjs)，复用现有 store/hooks/protocol 测试。

建议改法：

1. 保留状态文件单写者语义。短暂争用采用有总预算的等待重试，预算小于对应宿主 hook 超时并预留启动/落盘时间，不靠锁年龄抢活锁。
2. 对生命周期结束事件增加最小本机待处理记录：事件独立原子落盘，获得状态锁后幂等消费；只承接已识别的 Interrupt、StopFailure、SessionEnd，不做通用消息队列，不把 signal 自动重放成新授权。
3. 延迟事件绑定项目、session、宿主可用的 turn/event 标识及已知回合身份；缺少可信关联时保留待办并解释，不撤销新回合票据。重放、乱序、旧事件迟到必须有明确测试。
4. 入口拿不到身份时不得输出“入口已成功”的信息。等待预算耗尽后保守放行并给一次简短恢复提示；可重入事件由宿主下一次入口重建，不以创建猜测身份补救。
5. 任务中断按仍绑定该任务的有效 Lead 会话判断：结束当前会话并撤票，只有没有其他有效执行会话时才挂起共享 task。旧状态缺少新字段时保守兼容，不按 lastSeenAt 年龄强行判会话已死。
6. recovery guard 记录可核验的持有者信息并支持安全恢复；回收前重新确认目标身份，防止移走新锁。旧的空/损坏 guard 给受控诊断/修复出口，不能猜成死锁后删除。
7. 模型调用、知识扫描和可移出的上下文读取不占状态锁；涉及状态快照的结果在提交前复核。与 P02 分阶段完成，先保证语义，再缩临界区。

验收：

- 临时锁持有后释放，生命周期结束最终持久化；重复事件只生效一次。
- 旧结束事件不打断新回合；两个 Lead 共用 task 时结束其中一个不挂起另一方。
- 活锁、损坏锁、恢复期间另一个竞争者不被错误删除或覆盖；死持有者残留可恢复或得到可执行诊断。
- 状态读写失败不发继续执行决定，不伪造接收成功；不无限等待，不越过 hook 时间上限。

边界：不承诺磁盘不可写时仍能保存事件；不做全局任务自动超时结束。落盘失败如实报告，不把事件已进入内存当持久化成功。

### P02 可选知识与核心入口解耦

依据：格式错误的知识条目会让整个 projectContext 抛 KNOWLEDGE，openTurn 同次事务未保存；knowledge excluded 不受检索输出预算约束。unchanged 省输出不省检索，后者留 P11 测量。

涉及：[context](../../src/context.mjs)、[learning](../../src/learning.mjs)、[hooks](../../src/hooks.mjs)。依赖 P01 的锁/入口边界。

建议改法：

1. 先形成并可靠保存核心身份和回合状态，可选知识/对齐读取失败单独返回简短降级说明，不让其回滚核心入口。
2. 知识逐条解析：损坏条目跳过并保留诊断，仍召回有效条目；权限、路径/链接检查失败不降格为可写授权。
3. 自动入口只附命中、重要遗漏摘要和总数；excluded 设置条数/字符预算，完整诊断放显式查询。截断时明确数量，不能静默声称没有遗漏。
4. 同一故障没有变化时不每回合重复长错误；修复文件后能重新检索，不永久缓存失败。
5. 若调整异步上下文边界，输出前复核 session/turn；contextKey 只能标记实际成功生成的内容。

验收：一个坏条目不影响新 turn 保存、signal 接收和有效条目召回；缺失目录与 I/O 故障有可区分提示；大量未匹配条目不造成入口线性膨胀；修复后正常恢复。为这些失败行为补定向测试，不为每句提示写断言。

### P03 后台延期、冲突出口与调度补跑

依据：模型完成前前台启动，commitRun 因 BUSY 进入 recovery；前台结束后 reviewOnce 仍只回 recovery-required，需要手动 recover。旧 proposal 与用户新内容冲突时反复按旧 baseline 恢复仍冲突。tick 在后台锁竞争前已推进 lastCheckedAt，立即重试被 interval 延后，默认 15 分钟。

涉及：[review](../../src/review.mjs)、[scheduler](../../src/scheduler.mjs)，必要的 runner 接口测试。P01 完成后实施，与 P02 不并行改 hooks。

建议改法：

1. 区分可自动延期、内容冲突、执行失败和事务恢复。已有 proposal 因 BUSY/当前只读权限暂缓时保存原产物，后续 tick 在条件允许后先重试提交，不再调用模型。
2. 自动接续仍执行 maintenanceAllowed、baseline 和事务检查；前台未结束时只延期，不绕权限。
3. CONFLICT 不反复原样自动提交。提供明确的保留/作废旧提案并重排材料出口；作废不消费 inbox、不丢人工编辑，下一次新模型调用仍计入正常额度。
4. 未完成写事务先走既有恢复语义，不能把 committing/recovery 全部简单改成 pending。
5. 检查尝试与有效执行时间分开。锁争用、BUSY 等短延期不消耗整个正常检查周期；用有界下次机会接续，避免高频空跑。保持现有全局模型并发策略，不顺带改成多模型并发。
6. 已经启动但失败的模型调用继续占每日次数；仅重试落盘不新增一次模型额度，也不伪造 usage。

验收：假 runner 制造 BUSY 后，前台结束由后续 tick 完成，runner 调用次数仍为 1；连续 tick 不双写或双消费；真实内容冲突不覆盖用户修改，且有不用重复失败的退出路径；跨项目锁争用不强制额外等一个正常周期；损坏/未知事务仍保守保留。

## 5. 阶段 B：让对齐和门禁检查正确对象

### P04 增量对齐的来源基线收尾

依据：README 变化被 inspect 标为 stale，apply 成功写入对齐结论后再次 inspect，仍报告同一个 README 变化。apply 同传 decisions/findings 已支持，不重新开发。

涉及：[alignment](../../src/alignment.mjs)、对齐使用文档，必要时 P10 补输入参数。

建议改法：

1. 让一次对齐更新明确列出本次实际重读并确认的来源及读取时快照；仅更新这些来源的索引基线。
2. 提交前复核该快照。来源在读取后又变化则保留 stale，不能用“apply 成功”无条件确认整个项目。
3. 新增/删除来源按显式增量确认处理；新增资料仍可沿用 scan 的既有发现机制，不为本项重写扫描器。
4. 普通业务文档编辑、仅更新决定或建议，不自动代表所有来源已核对。
5. 保留对齐文档自身 baseline 检查与事务恢复，输出本次已确认/仍变化的简短结果。

验收：单来源变化确认后不重复提示；未确认来源仍 stale；确认期间再次修改能检测；删除/新增和混合 decisions/findings 一次提交可用；旧客户端不传确认来源时维持旧保守行为。

### P05 worktree、历史 ref 与重复 spec 检查

依据：task-end 使用 project.root 而不是附加 worktree；显式 `--ref` 的 Git 内容来自目标提交，但 spec 清单/code 来自当前磁盘，已分别复现误报与漏报。planBaselines 等相邻主 root 用法需在本包定向核对，不预先声称全部已复现。

涉及：[protocol](../../src/protocol.mjs)、[spec](../../src/spec.mjs)、hooks/CLI 的检查根传递、spec/计划说明。

建议改法：

1. 把可信 resolveProject 返回的当前 worktree 根传入任务检查；业务记录仍属于同一 project，不让 payload 任意指定全局路径。
2. HEAD/工作区检查保持既有工作区语义，采用当前 worktree 文件与 dirty 检查；显式历史 ref 先解析成固定 OID，spec 清单、正文、code 路径及代码内容均从该提交读取。
3. 历史提交没有 `.spec` 时按目标提交判无 spec，不混入当前定义；读取失败与无 spec 区分，不能失败后回退到 HEAD。
4. 顺查计划基线、回写提醒是否也应采用当前 worktree；只修确认同因的路径，公共知识 root 不随之机械切换。
5. `task-end` 保持权威 spec 检查；正常收尾不再要求先单独跑同一份 spec check。显式命令保留用于提前诊断；GATE 回执附可定位 findings，足以直接修复。
6. 文案改为“可在内容提交附 Spec-OK；需要追认既有历史时才按现有空提交语义使用”。不新设普通 waiver 绕过 spec。

验收：主树无变化、附加 worktree 有 drift 时正确拦；反向情况不误用主树；历史 spec 改路径/删除 spec 的误报和漏报都修复；无 spec、非法 ref、HEAD dirty、内容提交 Spec-OK 与既有空提交覆盖语义保持明确。测试使用临时 Git 库，不触及真实仓库分支/index。

## 6. 阶段 C：缩短接入与状态变更路径

### P06 安装入口修复与可选学习接入

依据：发布副本完好但 current 实际目标损坏，install 仍 already-installed；onboard 默认学习预检可阻断核心接入，即使未要求 enableLearning，虽有 skip-learning 出口。固定“代理必被宿主审批拦截”的文案不符合现场差异。

涉及：[install](../../src/install.mjs)、[onboard](../../src/onboard.mjs)、[context](../../src/context.mjs)，安装/接入说明。

建议改法：

1. install 提前返回前核对 current 实际目标与登记发布根一致；损坏的自有入口进入最小修复路径，正常重复安装保持幂等。
2. 修复前核对链接类型、归属和目标；用户替换的未知目录/链接不自动删除或接管，返回具体冲突。
3. 核心接入与可选学习预检分开。未请求启用学习时，学习问题提示后保留核心接入能力；明确请求启用学习时报告两个结果，不把学习失败写成全部成功。
4. 审批文案改为依据本次结果给下一步，保留用户手动入口，不要求本来可执行的代理操作一律交用户。

验收：临时 userDir 的断链/错链可修复，完好安装不重复改配置，未知目标保留；学习不可用仍可完成未要求学习的核心接入；显式学习失败有独立结果。当前阶段不以真实双宿主重装作为测试条件。

### P07 同任务的显式权限/目标变更

依据：同 task 重发 task-start 得到 accepted，但保留原 goal/permissions；这是现有接续约定与升级能力缺口，不能通过偷偷改变 task-start 语义修正。

涉及：[protocol](../../src/protocol.mjs)、[signal](../../src/signal.mjs)、CLI 帮助、知识/对齐授权测试和协议文档。

建议接口：独立 `task-update` 动作，明确修改 goal 与 permissions；首版不支持修改既定 route/channels、历史包或代替用户授权。名称是计划中的新接口，当前不存在。

1. 沿用当前身份、revision、票据与失败原子回滚；仅该任务有效 Lead 可改，独立 Worker/Reviewer 不能扩自身权限。
2. 允许更新任务当前有效 mode/allowedPaths，不把同任务必要扩范围逼成结束重开；调用方必须已经拥有对应用户授权。插件账本记录声明，不自动证明授权真实存在。
3. 宿主当前只读/plan 权限仍优先，不能靠 payload 提升宿主权限。仅更新本机任务声明，不改全局宿主配置。
4. 变更明确按替换或追加参数表达，回执返回有效权限及变更摘要；task-start 接续回执也说明保留了什么，避免 accepted 被误解。
5. 历史回执不重写，旧任务兼容。permissions 收缩不追溯取消已完成产物，但后续写入按新范围检查。

验收：plan→write 在用户/宿主条件满足后可完成；未满足条件拒绝且状态不变；追加/收缩、revision 冲突、重复请求/变正文、子角色拒绝、旧 task-start 兼容。直接 Edit/Write 不新增拦截器。

### P08 返修次数只统计交付后的返修

依据：previous.status 非 dispatched 就累加，failed/canceled 启动重派也算返修，与注释和协议描述不一致。

涉及：protocol 的 upsertPackages、返修/交付文档及 channels/gate 相关测试。

1. 以“此前是否有交付或审查要求修订”的事实计返修，不单凭当前 status 推断；必要时增加可选标记兼容旧包。
2. 同 packageId 重派和 supersedes 共享判定。启动失败重派不增加返修；交付后失败/取消再重派不能借状态绕开真实返修。
3. 历史 attempts 不凭猜测批量重算。旧记录保持可见，新增计数规则写清起点。
4. 两轮仍是提醒 Lead 判断的阈值，不改成硬拒绝；不删除已审包最终版本约束。

验收：连续三次未产出启动失败 attempts 不增长；交付后 FIX 重派与换 ID 继承正常增长；终态绕路不重置；旧状态可读取。无需为计数另建审计系统。

### P09 合并重复确认，按问题选择流程

涉及：公共工作方法、角色指引、design/validation/spec-plan/reports/delegation 参考页；hooks/protocol 仅修改对应已确认行为。

按以下规则修改，实施授权到来前不把建议当现行规定：

| 场景 | 建议行为与验收 |
| --- | --- |
| 已识别的结构化提问 | hook 自动记 waiting-user，不再要求先发一次 phase；不认识的工具和普通文本问题保留显式声明。一个结构化问题不产生两次语义相同状态修改 |
| plan 模式普通讨论 | 仅在本回合明确进入计划交付阶段时核对分包/通道/spec；普通解释不因 mode=plan 单独 block。不用扫描任意自然语言或文件名猜意图，不自动结束任务 |
| 计划交付通道 | 一次列明分包和所用通道；已有明确安排直接沿用，无 Worker 的任务不问 Worker。真实新增角色或通道才问，不删除计划交付时一次说明的要求 |
| 局部 UI 小改 | 已指定颜色、间距、文案等直接改现有组件并给实际效果；取消强制线框、每局部 2–3 方案和三步逐一选定。新信息架构、流程变化、整体改版保留必要方向确认；明确要求图片选方案时照做 |
| 测试和返修 | 包内及直接相关的常规检查默认预授权，但可能改数据/下载/外部服务的命令不一概叫只读。原范围且有新证据时继续定向修复，到提醒阈值只做一次裁决，不机械重开委派；无新证据的重复失败仍停止 |
| 项目文档明显错误 | 当前目标已包含文档修订且证据唯一时，可修断链、笔误、事实同步并简报；做法冲突、需求取舍、批准验收变化仍交用户。首次只读对齐不顺带越权改业务文档 |
| 文档写入与备份 | 普通人工任务编辑依现有文件工具和项目约定；插件维护的共享知识/对齐仍走事务。取消对可恢复已提交版本的机械重复拷贝；存在未提交/未跟踪用户内容时按实际风险保留最小非敏感备份 |
| 临时文件清理 | 可清理本任务创建、路径和所有权已知、无用户新增修改且无恢复价值的中间产物；未知/用户原有文件继续遵守可恢复删除要求。不得据此清 `.local/`、历史状态或其他会话材料 |
| 播报与经验 | 开始/范围实变时简短说明，无变化不重复目标和读取范围。无新经验不填模板；报告按复杂度写，不强制表格 |
| 独立审查 | 依据行为及失败代价，不按一行/文件数机械触发；已审交付对象变化时只复核相关差异和受影响证据，仍返回最终版本结论 |

验收采用规则逐条对照及少量场景 fixture。仅对等待状态与 Stop 行为写必要自动测试；UI、播报和模板文字不增加自动化框架。与 P05 的重复 spec 检查一起同步全部入口，避免短指引仍链接到旧的强制流程。

### P10 高频复杂载荷的一次调用路径

涉及：bin/signal/hooks 的可信调用识别，以及 knowledge capture、alignment 的输入帮助。依赖 P04/P07 的字段确定后再实施，避免反复改 CLI。

1. 先覆盖实际高频缺口：工作包派发/消费、单项审查结果、task-end validation，以及简短 capture；数组、多文件全文等继续支持 JSON 文件。一次消费并派下一阶段继续允许同批载荷。
2. 优先增加有限的结构化业务参数或可直接传递的 JSON/base64 选项，不实现通用 shell 解释器，不为每个深层字段造 flag。
3. 区分“CLI 能读 stdin”与“hook 接受管道信号”。新便捷路径必须从真实直接调用经过 PostToolUse 验证，不能只打印 JSON 就宣称已记录。
4. 对引号内普通 `->`、`&` 等字符的放行只在能证明两个宿主的实际分词/展开边界后实施；`$`、反引号及组合调用不因文案方便而随意放开。若成本过高，优先给安全直传载荷，不扩写 shellTokens。
5. 保留旧 --input/--base64、同请求回放与 revision 冲突语义。复杂长载荷超出宿主命令限制时明确回退文件，不承诺全部场景一调用。

验收：用相同的单 Worker+Reviewer 无返修流程，分别数派发/消费/验证的载荷准备与发送次数，报告实际减少值；含中文、引号、特殊字符及旧接口的真实命令文本 fixture 通过；伪造输出、组合命令与跨会话信号仍拒绝。不预设“减少 9–12 次”。

### P11 测量后再做的运行开销优化

本包先小测量，只有可复现收益才实施。以下是候选，不承诺全部完成。

| 候选 | 最小测量 | 候选措施及限制 |
| --- | --- | --- |
| 未接入目录仍先 verifyRelease | 普通 PostToolUse、未接入入口、已接入入口、signal、Stop 分开；记录文件读取/哈希和耗时 | 确认项目后再做重检查，或有明确失效条件的复用；不以 size/mtime 冒充内容完整性，不直接删除全部校验 |
| unchanged 前全量检索、对齐逐项检查 | 无变化回合、单文件变化、小/大知识库分别计 readdir/lstat/readFile、输出字符 | 将低成本版本判断前移，复用索引；跨进程缓存需明确失效与首次重查，目录 mtime 不能单独代表子文件内容没变 |
| no-op mutate 与全量状态序列化 | 新事件、重放/无变化事件、大小不同的合成状态对比 | 只在状态确实未变时跳写；保留观察事件、revision、迁移备份和事务中间 save |
| retired-locks 增长 | 合成锁次数与目录规模，观察写入/占用成本 | 正常自有锁可在证明 Windows 释放/恢复竞争语义后减少归档；历史文件清理另定显式范围，不自动扫真实存量 |
| preflight/接入反复检查 | 相同配置多次预检，配置变更一次 | 缓存只限可信稳定结果，配置变化失效；权限失败不缓存成成功 |

口径：固定同一机器/合成样本，进程内和真实 CLI 分开；建议每场景 9 次取中位数，耗时波动大才预定一次复测。可计 I/O 次数就不为毫秒增加复杂统计。字符数不当 token，工具次数不当模型轮次，没有真实 usage 不推算费用。

停止条件：未显示可复现改善、实现复杂度超过省下的步骤，或失效语义需要额外常驻服务时保留现状并说明。P02 的输出预算和故障隔离不等此测量。

## 9. 验证、回退与交付办法

1. 每个实施包先把上述已复现输入变成最少必要回归，再实现修正；复用现有 fixture，不建新框架。不同原因的边界各覆盖，不照抄实现逐函数测试。
2. 所有故障注入在临时 state/project/userDir 和临时 Git 库完成；模型链用假 runner，不跑真实收费复盘，不读真实宿主配置。
3. 每个独立交付阶段集成结束运行一次 `npm test` 和 `npm run check`；若连续集成同批而中间不交付，合并运行。之后只因新改动、失败或证据失效重跑相关验证。
4. 测试通过与真实宿主回调分开报告。真实安装、宿主重启、新 CLI 回执等未进入路径明确列待验；不为补齐这列自动重装。
5. 状态字段优先可选兼容；确需 schema 变化才沿现有备份迁移。回滚版本前核对新状态可读性，不能只回滚代码却忽略状态含义。
6. 失败不静默吞为成功：事件未落盘、恢复未完成、提案冲突、部分接入和检查失败分别报告。可选知识失败只隔离可选部分。
7. 每批回写本计划的完成项、偏离、剩余项与证据链接；不搬过程日志。达到该批验收即可结束，后续无收益项可明确延期。

最小收益核对使用四个场景：普通简单修改；单 Worker+Reviewer 的无返修流程；一次真实定向 FIX；模型完成与前台启动交错。只数协议准备/发送、用户新增确认、重复读取和人工恢复次数；耗时只在固定样本或宿主可用数据上比较。目标是减少必要目标之外的步骤，不向日常任务增加统计表。
