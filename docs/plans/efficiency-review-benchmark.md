# 基线 `ea54419` 与 `efficiency-review` 实测对比

本次在同一台机器、同一套合成状态上对比 `ea54419`（main，0.6.3）与 `2b1822c`（`efficiency-review`）：知识召回和典型调度的收益稳定且很大。300 条知识无变化回合入口约 573→104 ms（−82%），单条变化 900→226 ms（−75%），直接召回 519→72 ms（−86%）；未接入目录的入口从 15–23 ms 降到 0.6–0.7 ms（−95% 以上）。典型流程方面，带验证的 lead-direct 3→2 次工具调用，单 Worker+单 Reviewer 9→6 次（−33%），后台 BUSY 延期恢复的人工 `learning recover` 1→0（模型调用仍为 1 次）。明确的代价在锁争用：短持锁 400 ms 下当前版本等待后 5/5 成功、但中位数 210→457 ms（+117%）；超过预算的 2600 ms 持锁两者都降级，当前 226→1745 ms（+673%）。零知识的已接入入口和 300 项对齐检查在两次顺序复核中方向不稳定（约 −32%~+24%、12–20 ms），按噪声处理；除锁争用外没有可复现的 >15% 变慢。

> **需要先知道的变慢场景：锁争用。** 当前版本把“立即返回 LOCKED”改成“在预算内等待票据锁”：短争用从失败变成成功，但耗时约翻倍；长争用会等满预算后才降级，耗时约 8 倍。这是有意的时间换成功率，不是隐蔽的回退。若宿主对 hook 延迟极敏感，需要重新评估 `LOCK_WAIT_BUDGET_MS`/hook 预算；本次未修改生产代码。

### 1.4 锁争用（真实 CLI hook 子进程，计时含 Node 启动）

| 场景 | 基线 | 当前 | 变化 | 结果 |
| --- | ---: | ---: | ---: | --- |
| holder 持锁 400 ms，1 个 signal | 210.38 ms | 457.45 ms | +117.4% | 基线 0/5 回执、5/5 降级；当前 5/5 回执、0 降级；人工重试 5→0 |
| holder 持锁 400 ms，3 个入口 hook | 254.94 ms | 489.67 ms | +92.1% | 基线 0/15 成功、15/15 降级；当前 15/15 成功；人工重试 15→0 |
| holder 持锁 2600 ms，1 个 signal | 225.73 ms | 1744.76 ms | +672.9% | 两者均 5/5 降级；当前等满约 1.5 s 预算后才降级 |

锁场景每轮使用各版本自己的 `store.withLock` 由独立 holder 进程持有 state 锁；contender 是真实 `workflow hook` 子进程，统一传 `--state-dir`。基线在锁被占用时立即返回 `LOCKED` 并提示“保留待办”；当前版本在预算内等待，短争用因此成功。400 ms 持锁下当前的 457/490 ms 中位数包含约 400 ms 等待；2600 ms 持锁下当前的 1745 ms 是约 1.5 s 预算 + 进程启动/收尾。成功率的比较是这次锁改动的主要收益，延迟是明确代价；短争用 3 并发在本轮 15/15 成功，但已接近预算边界，不能外推为任意并发都成功。

## 2. 典型工作流：步骤对比

| 流程 | 基线（写 JSON/命令/总调用） | 当前（写 JSON/命令/总调用） | 变化 | 验证 |
| --- | ---: | ---: | ---: | --- |
| lead-direct 最小（task-start → task-end） | 0/2/2 | 0/2/2 | 无变化 | lifecycle complete |
| lead-direct + validation | 1/2/3 | 0/2/2 | −1 写、−1 调用（−33%） | validation 2 条证据 |
| 单 Worker + 单 Reviewer（无返修） | 4/5/9 | 1/5/6 | −3 写、−3 调用（−33%） | Worker consumed、Reviewer PASS、validation 2 条 |
| 后台复盘 BUSY 延期恢复 | 模型 1 / tick 2 / 人工 1 | 模型 1 / tick 2 / 人工 0 | 少 1 条人工恢复命令 | 最终 pending 0、知识 1 条 |

### 后台复盘 BUSY 细节

| 指标 | 基线 | 当前 |
| --- | --- | --- |
| 第一次 tick | `recovery` / `BUSY` | `deferred` / `BUSY` |
| 第二次 tick（+30 s） | `interval`（未接续） | `completed`，`resumed:true` |
| 模型调用 | 1 | 1 |
| 人工 `learning recover` | 1 | 0 |
| 第二次后 pending | 1 | 0 |
| 最终 pending / 知识条目 | 0 / 1 | 0 / 1 |

基线第一次 tick 在 review 前推进 `lastCheckedAt`，第二次 tick 因此只返回 `interval`，需要人工 `learning recover`；当前版本把 BUSY 记为 deferred、不推进 `lastCheckedAt`，30 秒后的下一次机会只重试提交，不再调用模型。两边的模型调用次数都是 1，节省的是人工命令，不是模型成本。

## 3. 测量方法

- 两个版本都用 `git archive <ref> | tar -x -C <系统临时目录>` 取出副本运行；没有改动当前仓库 worktree，也没有使用真实宿主安装。
- 所有状态、项目、发布副本、CLI 参数都在系统临时目录；CLI 一律显式 `--state-dir`；后台复盘使用假 runner/假 preflight，不调用真实模型。
- 进程内测量：包装 `node:fs/promises` 的 `readFile/writeFile/readdir/lstat/stat/open/rename/mkdir/realpath/copyFile/symlink/unlink/access/cp` 与 `crypto.createHash`，用 `syncBuiltinESMExports()` 同步到 ESM 命名导入；目标版本源码不改。I/O 数字是“包装到的调用次数”，不是系统调用总数。
- 时间：每个进程内场景 9 次取中位数；每次 hook 测量都从同一份种子状态复制，复制与预热在计时之外。CLI/锁场景是真实子进程，计时含 Node 启动。
- 知识：300 条合法合成条目，另加解析失败、字段类型错误各 1 条；入口场景带 active 任务，否则两个版本都不会在入口检索知识。索引在测量前预热一次；变化场景通过 `renderEntry` 生成正文与元数据一致的条目。
- 对齐：300 个合成资料的逐项检查；增量场景每轮新建项目/状态，改 README 后测 apply + 复核，避免上一轮的 `docs/WORKFLOW-ALIGNMENT.md` 影响下一轮。
- 锁：每轮独立 holder 进程 + 真实 CLI contender；400 ms 短持锁测 1 个 signal 和 3 个并发入口，2600 ms 长持锁测 1 个 signal；每档 5 轮。
- 工作流：真实 CLI 子进程，命令文本和真实 stdout 再经当前版本的 PostToolUse 回执验证；只数“写 JSON 文件/发送命令/两者合计”，不推算模型轮次或费用。
- 顺序复核：另按 `current→baseline` 顺序重跑 9 次，专门检查入口这类小绝对值场景是否受“先跑/后跑”影响。

## 5. 机器与样本量

- CPU：13th Gen Intel(R) Core(TM) i5-13400F
- OS：Windows 11（`Windows_NT 10.0.26200`），`win32 x64`
- Node：v24.21.0
- 进程内/入口/知识/对齐：每个版本 9 次；锁：每档 5 轮；工作流：每条 1 次；后台复盘：每条 1 次；顺序复核：两种顺序各 9 次。
- 合成发布副本约 50 个文件、约 620 KB；知识 300 条；对齐资料 300 个。

## 6. 复现

```bash
# 1. 取两个版本的副本（示例；路径放到系统临时目录）
git archive ea54419 | tar -x -C "<临时目录>/baseline"
git archive 2b1822c | tar -x -C "<临时目录>/current"

# 2. 运行对比（--repeat-order 会额外按相反顺序重跑入口场景）
node scripts/bench/compare.mjs \
  --baseline "<临时目录>/baseline/bin/workflow.mjs" \
  --current "<临时目录>/current/bin/workflow.mjs" \
  --runs 9 --rounds 5 --repeat-order --json \
  --out-json docs/plans/efficiency-review-benchmark.json
```

原始数据见 [efficiency-review-benchmark.json](efficiency-review-benchmark.json)。脚本会自动在 `finally` 中用 `trash` 清理临时目录；不含真实状态、真实宿主配置或凭据。

## 7. 局限与未测项

- **合成样本**：不是真实大型 Git 仓库，项目只有少量文件和 300 条知识/对齐资料；绝对毫秒数依赖机器，结论只用于同机相对比较。
- **计数包装有开销**：I/O 数字是包装到的调用次数，包装本身增加函数调用开销，且可能漏掉不经过这些绑定的内部 I/O；不要当作真实 syscall 数或磁盘吞吐。
- **锁计时含进程启动**：锁场景是真实 CLI 子进程，约 150–250 ms 的 Node 启动计入中位数；holder 的就绪等待不计入 contender。Windows 文件/进程调度与 Linux 不同，未做跨平台复测。
- **后台复盘是假执行器**：只验证 BUSY/延期/恢复的控制流与模型调用次数，不验证真实模型输出质量、token、费用或宿主计划任务；一次观测、一个知识条目，不外推。
- **未测真实宿主安装/凭据/计划任务**，未读写 `~/.claude`、`~/.codex` 或真实 workflow 状态；未测真实网络与真实 Codex/Claude 会话。
- **工作流只数结构步骤**：写文件/命令/工具调用是确定性计数；不推算模型轮次、token 或费用，也不代表实际墙钟时间。
- **坏条目的基线中位数是失败样本**：解析失败场景基线 9/9 抛错，当前 9/9 成功；该行用于说明健壮性差异，不用于速度排名。
- **小绝对值场景按噪声处理**：已接入零知识入口、300 项对齐检查、普通 PostToolUse 的百分比在多次运行中方向翻转，不能作为回归或优化结论。
- **锁的变慢是有意权衡**：短争用成功率的提升以等待时间为代价；长争用会等满预算。是否接受取决于宿主对 hook 延迟的容忍度，本次未调整预算常量。
- **未做 token/费用外推**：没有真实模型调用，不能从命令数推导账单变化。

## 8. 本次未改生产代码

只新增 `scripts/bench/compare.mjs`、本说明和 JSON 数据；`src/`、版本号、发布清单均未修改。锁的延迟回退、以及入口/对齐小绝对值场景的顺序敏感性，均作为测量结果报告，未在本分支修复。
