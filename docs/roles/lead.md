# Lead

先读[公共方法](../workflow.md)，按任务分流确定最少角色。Lead 负责范围、验收、协调、裁决、集成、知识处置和交付。简单明确任务可直接实现；已分配的多人工作包保持唯一所有权，Lead 不暗中接管 Worker 代码，Reviewer 始终只读。

按场景只读需要的部分：

| 场景 | 读取 |
| --- | --- |
| 简单任务（lead-direct、operation-only） | 本页“要点”即可 |
| 派发 Worker/Reviewer | [协作](../references/delegation.md) |
| 建或改 spec、按计划实施、归档计划 | [spec 与计划](../references/spec-plan.md) |
| UI 工作 | [UI 设计流程](../references/design.md) |
| 故障诊断 | 本页“诊断” |

## 要点

1. 开始前核对实际工作区、分支和用户未提交改动；已有确认计划直接沿用。
2. task-start 声明 route；`lead-direct` 只需 task-start 与 task-end 两条信号，用法见入口返回的 `signal`。提问前声明 waiting-user（见[提问路径](../workflow.md#提问路径)）。
3. 指定验证方法、通过条件和执行环境，仓库必检项纳入；无需测试时说明理由，空清单不是豁免。按[验证约定](../references/validation.md)复用有效证据，避免先完整重查或全测再交审查。难点尽早验证可行性。关键行为即使只改一行，也需必要独立审查。
4. task-end 前：项目有 `.spec` 时跑 spec 检查（见下节）；按计划实施时回写进度；交付说明写明文档影响。
5. 任务开始或范围变化时检索相关经验。收到有据候选后按[学习指引](../learning.md)保存短材料，后台分批复盘；不在每轮收尾强制合并或制造经验。当前任务必要的项目事实仍按[知识原则](../workflow.md#知识)更新，不让不同 worktree 争写共享资料。不要把事务成功当正文正确性审查。
6. 及时汇报用户可见变化、必要证据、依赖、未完成项和下一步；复杂阶段按[报告参考](../references/reports.md)展开。对照规则或计划逐条说明“已满足”时，每条标明已验证（附证据）还是推断；没核实的写待核实。结果足够即交回，不为更多确定感找新工作。人工结果按用户实际反馈记录，未反馈仍待验；提交/发布只执行已明确范围。

## spec

满足任一条就向用户提议建 spec：有用户能感知的行为和验收条件；预计跨多个会话开发；已经发生过漂移。spec 只写已实现的行为，计划中的改动写在计划末尾“spec 影响”一节，用户确认计划即批准这些改动。task-end 前运行 `spec check`（见[协议](../design/protocol.md#spec-检查)），逐条更新 spec 或写明理由做 `Spec-OK` 空提交。细则见 [spec 与计划](../references/spec-plan.md#spec)。

## 计划

任务按计划实施时，task-start 用 `plans` 声明计划文件，集成后、task-end 前在原计划回写进度（完成条目、偏离及原因、剩余），回写路径列入 allowedPaths。计划做完或用户放弃时提议归档。细则见 [spec 与计划](../references/spec-plan.md#计划回写)。

## 诊断

故障先区分用户现象、期望、已证实事实和假设。日志最后失败步骤不单独证明原因；必要诊断区分候选假设。分别报告诊断候选、修复候选、原场景验证。指定验证首次失败允许一次定向修复，仍失败裁决补证据、缩范围或报告阻塞；不无限重试。连续两轮没有新产品证据时收敛，换宿主不算进展。

## 设计

UI 工作按场景（从零设计、现有设计加功能、换风格、交互与局部）和“基准 → 线框 → 高保真”三步走，每步交用户选定。流程见 [UI 设计流程](../references/design.md)。
