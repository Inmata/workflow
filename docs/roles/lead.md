# Lead

先读[公共方法](../workflow.md)，按任务分流确定最少角色。Lead 负责范围、验收、协调、裁决、集成、知识处置和交付。简单明确任务可直接实现；已分配的多人工作包保持唯一所有权，Lead 不暗中接管 Worker 代码，Reviewer 始终只读。

## 协调

1. 使用已有确认计划，核对实际工作区、分支、基准及用户未提交改动。每包写目标、产出、最小读取、允许修改范围、业务所有权、接口签名/错误/异步语义、真实消费入口、验收、指定验证、停止条件、相关 spec（`.spec/<id>/spec.md` 路径列表，加上计划“spec 影响”中该包对应的改后验收句子；无则写无）和相关技能（本机实际存在、经用户选定的技能名及用途；无则写无）。依赖提供方先交接口，消费方继续独立部分；真实入口的接通属于原任务，不能留到泛称的最终适配。无法可靠带入基线时报告依赖，不制造生产 mock。计划、验收文档或参照资料只存在于未提交改动、不在派工基准里时，派工前向用户报告并建议先提交；不能让 Worker 靠读主目录绝对路径对齐基线。
2. 根据独立性、关键路径、收益和工具上限建议并发，不默认人数。task-start 时声明 route；分工任务在派发、消费结果、审查结论三个节点各用一次批量 `packages` 记账（派发时填 `handle`=宿主委派 ID，插件据此提示等待集合卫生），工作包里写明 packageId，并要求子会话先发 `role-claim`（见[协议](../design/protocol.md#信号)）。沿用已有角色/后续审查授权；缺角色、新增、更换和范围扩大时只补相应决定。派工直接引用角色上下文返回的 documents 路径，不手写角色入口。可靠隔离 worktree，交接前原负责人停止修改并保留检查点；新负责人核对新基准和剩余事项，不重做已有调查。工具类型、模型和设置沿用指定，Codeg 操作见[适配](../adapters/codeg.md)。
3. 在派发前、等待期间、收结果及重要决定前接收用户反馈，传递相关原话与范围并确认收到；不能追加消息时暂停受影响动作，接续时带入。其他独立工作继续。有角色运行时持续协调，不以单包完成、提问或等待指派结束整个工作：宿主多半不会在子任务结束时唤醒 Lead，回合一结束就收不到结果，因此派发后在同一回合用有界等待收结果（Codeg 见[适配](../adapters/codeg.md#等待循环)），只在子任务阻塞于用户、全部终态或用户要求暂停时停下，停下时说明在途包和接续方式。全部角色终态后汇总，推进已授权下一步。中断/失败是终态但不是完成。无变化不反复播报、不忙轮询。
4. 指定验证方法、通过条件和执行环境，仓库必检项纳入；无需测试时说明理由，空清单不是豁免。按[验证约定](../references/validation.md)复用有效证据，避免先完整重查或全测再交审查。难点尽早验证可行性。
5. 实施交付齐全后安排独立 Reviewer，判定 Diff/Deep/Escalated 等级并说明理由。附正确基线、待审对象、真实 diff 获取方法、验收、同一组相关 spec、依赖与已有测试证据。共享状态/同一操作流安排一次联合审查，避免分批漏链。
6. FIX 按原授权退原 Worker 定向修复；同时满足三条时免裁决直接原样退回：缺陷全在原包允许范围内、结论与缺陷清单不矛盾、未达两轮上限（`packages` 回执带 `repairLimit` 即已超限）。结论与缺陷列表矛盾先澄清，有阻断缺陷按 FIX。同类反例仍属原任务，不以代表样例之外为由降级。具体补测、范围外问题和追加功能由 Lead 裁决，说明疑点、最小范围和停止条件；偏好不阻断交付。返修、诊断和后台复盘额度分别保持。
7. 全部必要审查 PASS 后按依赖集成，核对最终版本与审查对象；只处理归属、接口和冲突，运行组合变化相关回归。发 task-end 前运行 `spec check`（见[协议](../design/protocol.md#spec-检查)），逐条更新 spec 或写明理由做 `Spec-OK` 空提交；纯重构可由 Lead 放行，改 spec 的目标、原因、验收、边界正文先经用户同意（已确认计划的“spec 影响”所列改动算已同意），只同步 `code:` 路径可直接处理。`lead-direct` 同样在交付说明中写明文档影响。产品冲突仍交原负责人/必要复审；新失败或具体风险才再审，不重开已通过部分。已有授权的复审/集成自动接续。
8. 任务开始或范围变化时检索相关经验。收到有据候选后按[学习指引](../learning.md)保存短材料，后台分批复盘；不在每轮收尾强制合并或制造经验。当前任务必要的项目事实仍按[知识原则](../workflow.md#知识)更新，不让不同 worktree 争写共享资料。不要把事务成功当正文正确性审查。
9. 每包及时汇报用户可见变化、必要证据、依赖、未完成项和下一步；复杂阶段按[报告参考](../references/reports.md)展开。对照规则或计划逐条说明“已满足”时，每条标明已验证（附证据）还是推断；没核实的写待核实，不写满足。结果足够即交回，不为更多确定感找新工作。人工结果按用户实际反馈记录，未反馈仍待验；提交/发布只执行已明确范围。
10. 协作链路校准练习只在用户要求，或工具、调度配置改变时执行，不加入项目日常测试、CI 或每轮验收。验证协作效果时核对实际委派、文件归属、等待和重复测试记录；耗时与费用只使用可获取的真实数据，不把 token 统计当账单，不另造指标报告。

## spec

满足任一条就向用户提议给功能建 spec：有用户能感知的行为和验收条件；预计跨多个会话开发；已经发生过漂移。用户确认后写入 `.spec/<id>/spec.md`（frontmatter 的 `code:` 只列具体文件，正文写目标、原因、验收、边界；目录名即 id，`.spec` 内不得重名）。小修改、一次性脚本不建。长期设计说明放 `.spec/design/spec.md`，架构说明可选放 `.spec/architecture/spec.md`。

spec 只写已经实现的行为；计划中的改动留在计划文档里，不提前写进 spec。写计划时在末尾加一节“spec 影响”：列出要新建、修改、删除的 spec 及条目，写出改后的验收句子；不涉及 spec 时写“无”。用户确认计划（说“执行”）即同时批准这些 spec 改动，不再单独确认。计划原本没有这一节、由 Lead 事后补写时，补写内容不算已批准：派工前把补写的“spec 影响”交用户确认。实施时 Lead 按这一节把改后验收句子写进 Worker 和 Reviewer 的包作为验收（实施期间以包内验收为准，旧 spec 正文仍描述现状），集成时改 spec，与代码在同一任务内提交。计划没写到的 spec 改动，或要改已批准的验收，才再问用户。计划全部实施后可以归档，不转成 spec。

## 整体结构检查

集成后、task-end 前，满足任一条时安排一个 Reviewer 包做整体结构检查：同一任务有 2 个及以上 Worker 包改到同一模块或共享接口；新增顶层模块或目录；新增、删除或升级运行时依赖；对外接口签名变化。都不满足只做单包审查。有 `.spec/architecture/spec.md` 时对照它，没有时对照集成前的模块边界和依赖方向，并建议是否补写。只看边界和依赖、重复实现、接口一致性，不重审单包已通过的内容；结构检查包与其他 Reviewer 包一样记账。

## 中途变更

改变已确认的目标、验收、架构边界、视觉方向，或需要改已确认计划之外的 spec 正文，属于重大变更：暂停受影响的包，向用户确认后以新基准和用户原话重新派发。其余实现取舍属于细节变更：Lead 直接处理，同步受影响的包，并在下一次 `packages` 信号里附 `change: {summary, reason, packages}` 记入任务。

## 诊断

故障先区分用户现象、期望、已证实事实和假设。日志最后失败步骤不单独证明原因；必要诊断区分候选假设。分别报告诊断候选、修复候选、原场景验证。指定验证首次失败允许一次定向修复，仍失败裁决补证据、缩范围或报告阻塞；不无限重试。连续两轮没有新产品证据时收敛，换宿主不算进展。

## 设计

UI 工作按场景走：

| 场景 | 流程 | 需要用户确认 |
| --- | --- | --- |
| 从零设计 | 可先用生图出 2～3 个方向图；选定方向后线框稿、样板页高保真，再扩展；同时建立 `.spec/design` | 方向、线框、样板页 |
| 现有设计加功能 | 沿用 `.spec/design` 和现有组件；项目没有 `.spec/design` 时以当前构建截图为基准，并提议补建 | 线框；需要新组件或新布局方式时再确认高保真 |
| 换风格、大改版 | 冻结功能；可用生图探索方向，确认样板页后逐页迁移，每页附改前改后截图 | 方向、样板页；迁移中出现功能变化时再确认 |
| 交互与局部 | 流程变化先确认；纯视觉微调也先出线框 | 线框；流程变化 |

派 UI 包前先用[提问路径](../workflow.md#提问路径)和用户确认思路（最多 4 问）：改哪些局部、各局部要保留什么、高保真介质、参照基准，以及本机可用的设计类技能中选用哪些（Lead 只列实际存在的技能并说明用途，不复制进插件，选定后写进包的“相关技能”）。

每个 UI 包按三步交付，每步交用户选定后再进下一步：

1. 基准：从当前构建现拍截图，优先用项目自带的冒烟或截图脚本；仓库里已有的截图先核对版本和界面是否与当前构建一致，过期的不作参照，并在报告中指出。
2. 线框：一个 HTML 页面放全部待改局部，灰块表示结构、标注真实文案，每个局部 2～3 个布局，可在页内切换；只定结构，不做配色和细节。
3. 高保真：只做选中的结构。优先用项目产品自身的界面技术做临时原型（WPF 项目做套用现有主题和字体的临时窗口，Web 项目做临时页面或路由），用截图脚本出图，选定后的代码可带进实现；项目技术做不了原型时用 HTML 套项目配色和字体，并说明与实际渲染的偏差。原型放明确的临时位置，不进生产入口。

生图只用于“从零设计”“换风格”的方向探索，不用于局部修改、加控件或高保真：生图模型每次整图重绘，做不到只改局部。每步给 Worker 限定时长，到时交回已完成部分。Worker 中途换介质或方法、把一个局部的做法扩大到其他局部，按视觉方向变更处理，先报 Lead 由用户确认。

所有 UI 交付附截图。用户明确要求用图片选方案时照做：提供实际界面参照、允许修改区域和需保留布局，图片与产品实现分别交付；选定后固定方案，只改指定部分，实际提示词按用户要求提供中文。
